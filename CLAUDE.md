# Repository conventions

## Ownership

- Pablo Motta authors and is responsible for all code in this repo, including changes made with AI assistance. Do not attribute authorship, generation, or co-authorship to any AI tool anywhere: not in commits, branch names, PR titles/descriptions, PR comments, code comments, or any other repo content.
- Never add AI attribution or watermarks: no "Generated by", "Created by", "Co-Authored-By", session links, or similar trailers and footers.
- Everything in this repo should read as if Pablo wrote it, with no mention of the tool used to produce it.

## Git

Agents may commit, push, merge, and open pull requests without asking, unless told otherwise in the request. Two things are not optional:

- **Every commit must be authored by Pablo Motta.** Set the identity explicitly rather than relying on whatever the environment defaults to:
  ```
  git -c user.name="Pablo Motta" -c user.email="pmotta.dev@gmail.com" commit …
  ```
- **Verify after committing**, before moving on:
  ```
  git log -1 --format='%an <%ae>%n%b'
  ```
  The author must be `Pablo Motta <pmotta.dev@gmail.com>`, and the body must contain no `Co-Authored-By`, no session link, no tool name. If either is wrong, amend before pushing. If it is already pushed, say so plainly rather than quietly leaving it.

Never rewrite pushed history — no rebase, amend, or force-push on a branch that exists on the remote — unless explicitly asked.

## Branch naming

- Never prefix branches with a tool name.
- Use conventional prefixes: `feature/`, `fix/`, `chore/`, `docs/`.
- Push README-only or otherwise non-breaking changes straight to the default branch. Anything that changes behaviour goes on a branch.

## Commit messages

One concise line in [Conventional Commits](https://www.conventionalcommits.org/) format:

```
<type>: <short description in imperative mood>
```

**Types:** `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`, `build`, `ci`, `perf`, `a11y`

**Rules:**

- Lowercase type prefix. No scope unless it adds clarity (e.g. `fix(a11y): …`).
- Imperative mood: "add labels", not "added labels".
- Subject line ~72 characters max. Add a body only when the reason for the change is not obvious from the diff; keep it to what a reviewer could not infer.
- Describe what and why, not a file list.

**Examples:**

```
feat: add skip link and main landmark
fix: meet AA contrast on muted text
fix(a11y): add visible labels to contact form
docs: add WCAG audit report
chore: update resume link
```

## Pull request descriptions

```markdown
## Summary of Changes

<!-- If related to a ticket, summarize what the ticket is about, with the ticket number. -->

<!-- A list of changes, each with a concise explanation. -->

<!-- If there is visual impact, concisely explain it. -->

<!-- If this fixes a bug or adds a feature, explain how to validate it. -->
```

**Rules:**

- Never include watermarks or any mention of tooling.
- Never repeat what is already implied or explained elsewhere in the PR.
- Never state the obvious. If a change was requested, do not write "I did this as requested" or restate the request back.
- Omit a section rather than padding it. A PR with two real bullets beats one with four filler ones.
- Explain what a reviewer cannot see from the diff alone.
- After creating or updating a PR, read the body back from the GitHub API and confirm no footer or session link was appended server-side. If one was, strip it with a follow-up update.

## Accessibility

Target WCAG 2.2 AA. These are requirements, not suggestions:

- **Semantic HTML first.** Use the real element — `button`, `a`, `nav`, `main`, `h1`–`h6` — before reaching for a `div` plus ARIA. ARIA is a patch for when no native element fits.
- **One `h1` per page**, headings in order, no levels skipped for styling.
- **Every page has a `main` landmark** and a skip link to it as the first focusable element.
- **Every control has an accessible name.** Visible `label` for form fields; `aria-label` only when a visible label genuinely cannot exist.
- **Every image has `alt`.** Decorative images take `alt=""`, never a filename or "image".
- **Contrast:** 4.5:1 for body text, 3:1 for large text and UI boundaries. Check it, don't estimate it.
- **Keyboard:** every interactive element reachable and operable by keyboard, in a sensible order, with a visible focus indicator. Never remove focus outlines without replacing them.
- **Do not convey meaning by colour alone.**
- **Respect `prefers-reduced-motion`** for anything that animates.

Run the check before handing work over, and report the result:

```
npx @axe-core/cli <url> --tags wcag2a,wcag2aa,wcag21aa,wcag22aa
```

Fix what it finds or explain why a finding is a false positive. Never report work as done on a check that was never run — say which checks ran and which did not apply.
