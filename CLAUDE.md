# Repository conventions

## Ownership

I author and am responsible for all code in this repo, including changes
made with AI assistance. Never attribute authorship, generation, or
co-authorship to Claude, Cursor, or any other tool: not in commits,
branch names, PR titles or descriptions, PR comments, code comments, or
any other repo content. No "Generated by Claude Code" footers, no
`Co-Authored-By: Claude` trailers, no session links.

## Git: the user commits

- **Never** run `git commit`, `git push`, or `git add` for the purpose of committing unless the user **explicitly** asks in that message (e.g. "commit this", "create a PR").
- "Implement the plan", "fix this", or "apply the changes" does **not** mean commit.
- After making changes, leave them uncommitted and say what the user should review.
- If the user asks for a commit message, provide the text only. Do not run `git commit`.
- Do not push, open a PR, or rewrite pushed history unless explicitly asked.
- Before handing off any commit, run `git log -1 --format='%an <%ae>'` and confirm the author is the repo owner, not Claude or any other tool identity.

## Branch naming

- Never prefix branches with `claude/`, `cursor/`, or any other AI-tool name.
- Use conventional prefixes: `feature/`, `fix/`, `chore/`, `docs/`.

## Commit messages

One concise line in [Conventional Commits](https://www.conventionalcommits.org/) format:

```
<type>: <short description in imperative mood>
```

**Types:** `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`, `build`, `ci`, `perf`, `a11y`

**Rules:**

- Lowercase type prefix. No scope unless it adds clarity (e.g. `fix(a11y): …`).
- Imperative mood: "add labels", not "added labels".
- One line, ~72 characters max. **No body** — the structured detail belongs in the PR description.
- Describe what and why, not a file list.

**Examples:**

```
feat: add skip link and main landmark
fix: meet AA contrast on muted text
fix(a11y): add visible labels to contact form
docs: add WCAG audit report
chore: update resume link
```

## Pull request descriptions

Every PR body uses this template:

```markdown
## Summary of Changes

<!-- If related to a ticket, summarize what the ticket is about, with the ticket number. -->

<!-- A list of changes, each with a concise explanation. -->

<!-- If there is visual impact, concisely explain it. -->

<!-- If this fixes a bug or adds a feature, explain how to validate it. -->
```

**Rules:**

- Never include AI watermarks or any mention of tooling.
- Never repeat what is already implied or explained elsewhere in the PR.
- Never state the obvious. If the user asked for a change, do not write "I did this as requested" or restate the request back.
- Omit a section rather than padding it. A PR with two real bullets beats one with four filler ones.
- Explain what a reviewer cannot see from the diff alone.
- After creating or updating a PR, read the body back from the GitHub API and confirm no "Generated by Claude Code" footer or session link was appended. The GitHub MCP server adds one server-side after the body is submitted, so strip it with a follow-up update.
